# Conformance tooling

How the denominator is built and how results are classified. Change anything here with care:
these components decide what "green" means.

## Pipeline

```
pinned sources
   │
   ├─ BUILD files ─────┐
   ├─ cargo metadata ──┤
   ├─ .feature files ──┼─▶ corpus-catalog ─▶ catalogue (258 targets, 4 757 leaf cases)
   ├─ failpoint registry ┤                        │
   └─ built harnesses ──┘                         ▼
                                          conformance-runner
                                                  │
                                                  ▼
                                       coverage report + verdict
```

## Three independent readings, then reconciliation

No single reading of the corpus is trustworthy:

* **`cargo metadata`** — but the root `Cargo.toml` is generated by a Bazel-invoking sync tool,
  so Cargo can omit targets BUILD declares.
* **BUILD files** — parsed directly, so a target that never reached Cargo is still counted.
* **The corpora** — Cucumber scenarios and the failpoint registry, whose leaf cases exist in
  neither of the above.

Anything present on one side and missing on the other is a reconciliation finding, never a
silent drop.

## Rules that must not be weakened

| Rule | Why |
|---|---|
| An unreadable outcome is `Unknown`, never a pass | the core no-false-green rule |
| Duplicate results merge to the **worst** verdict | a retry must not manufacture a pass; a skip must not mask a failure |
| A target with catalogued cases that runs zero is a failure | catches a harness filtering itself to nothing |
| A reported case absent from the catalogue fails the run | means the denominator is wrong |
| Timeouts kill the process group and are never green | an orphaned server breaks every later target |
| `SCENARIO_FILTER`/`FAILPOINTS`/`RUST_TEST_ARGS` refuse the run | each would silently shrink the corpus |

## Composite harnesses

Three suites hide many cases behind few libtest cases. Each has its own attributor, and each
may say "I don't know" — see [ADR-0003](../architecture/ADR/0003-conformance-runner-no-false-green.md).

* **Cucumber** — per-scenario results parsed from the writer's output, cross-checked against
  the `[Summary]` totals. A mismatch downgrades the whole target to `Unknown`.
* **Failpoints** — deliberately asymmetric: a passing loop credits all 22 members, a failing
  loop credits none. Under-reports, never over-reports.
* **Benches** — `harness = false`, so one leaf case per binary from the exit status.

## Traps that already bit

Each of these cost a full diagnostic cycle. They are listed so you do not repeat them.

| Trap | Symptom |
|---|---|
| `select()` flattened across all branches | Linux run told to extract a Windows `.zip` |
| Bazel `glob()` crossing package boundaries | a checkstyle target failing on a file upstream never inspects |
| `--nocapture` on plain libtest targets | statuses read as test output |
| `tracing` writing to fd 1 | verdicts pushed onto later lines; cases read as `Unknown` |
| `data` treated as "what runs" | 6 scenarios counted from a feature nothing opens |
| One ignore predicate assumed | the corpus has two, and they disagree |

The general shape: **a rule reproduced in form but not in semantics.** When porting a Bazel
behaviour, read its definition rather than inferring it from the call site.

## Extending the catalogue

Adding a new kind of leaf case means touching:

1. `corpus-catalog/src/model.rs` — the `LeafKind` and `CaseDiscovery` variants
2. `corpus-catalog/src/lib.rs` — generation
3. `conformance-runner/src/lib.rs` — an attributor, which must be able to return `Unknown`
4. A unit test proving the attributor does not manufacture a pass

The schema at `contract/typedb-r2-v14-upstream-test-catalog.schema.json` validates every
generated catalogue, so the two cannot drift apart.
