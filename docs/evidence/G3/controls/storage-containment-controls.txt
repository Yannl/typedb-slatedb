## Q-14 - a failed object-cache wipe is propagated, not discarded
The FIRST version of this control was wrong and is recorded here because the
mutant caught it: it injected a non-directory at the cache path and asserted
that `open_remote` failed. It passed under the mutant, because `create_dir_all`
fails on the same obstruction whether or not the wipe's error is discarded -
so it proved nothing. The failure that actually matters is a PARTIAL wipe:
`remove_dir_all` deleting some entries and erroring midway leaves the directory
present, `create_dir_all` then succeeds, and the survivors are served for this
materialisation's object paths.

The wipe is now a named function and the control asserts its own result.

## Q-13 - object-store retries are BOUNDED
`settings.object_store_max_retries = Some(8)` in `SlateKeyspace::settings()`.
Upstream default is unbounded retry, which converts a persistent R2/S3 fault
into an infinite silent stall of the flush path. Bound chosen with the bridge
deadline below (OD-006). No standalone mutant: the setting is a constant read
by the upstream crate, and the assertion that would observe it (a fault
injected 9 deep) belongs to the failpoints lane; the value is asserted by
inspection in settings() and covered by the compile-time type (Option<u32>).

## Q-23 - the async->sync bridge is BOUNDED and LOUD
`bridge()` waits with `recv_timeout(30s)` in a loop: every 30s it logs an
ERROR naming the operation still pending; at 600s it `std::process::abort()`s
(fail-stop beats a silent forever-hang holding storage locks — same doctrine
as Q-01). A disconnected channel (runtime died mid-operation) panics
immediately instead of returning garbage. Deadline + retry bound recorded as
OD-006 in docs/owner-decisions.json.
No mutant executed: killing the deadline means a 600-second hanging test per
run, which the flake-ledger doctrine excludes from the fast suite; the
failpoints lane owns the induced-stall measurement (NEXT-SESSION item).

## Q-22 - cursor drop order is STRUCTURAL, not declaration-order
`RocksCursor` holds `iterator: ManuallyDrop<DBRawIterator<'static>>` plus
`Arc<DB>`; an explicit `Drop` impl drops the iterator first, always, so field
reordering can no longer reintroduce the use-after-free. The control also
proves co-ownership: the cursor keeps the DB alive after every other handle
is gone.

CONTROL: keyspace::cursor::rocks_cursor_tests::
         a_cursor_keeps_its_database_alive_after_every_other_handle_is_gone
MUTANT: fields reordered `db` first, plain iterator field, `Drop` impl and
        `ManuallyDrop` removed — i.e. the audited defect reintroduced
        (drop order back on declaration order, db dies first)
  running 1 test
  pthread lock: Invalid argument
  process didn't exit successfully: (signal: 6, SIGABRT: process abort signal)
  -> restored: test result: ok. 1 passed (filtered); full suite 27 passed; 0 failed

  Caveat, recorded honestly: the mutant dies via undefined behaviour
  (iterator destroyed after its DB), so the SIGABRT is an observed outcome,
  not a guaranteed one — UB is not required to crash. It DID kill the mutant
  on this toolchain (rustc 1.93.0, librocksdb-sys bundled), and the structural
  ordering plus the co-ownership assertion are the durable closure.
